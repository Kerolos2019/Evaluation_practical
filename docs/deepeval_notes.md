## Understand DeepEval

### Module 1: What is LLMTestCase

#### Creating Your First `LLMTestCase`

In the previous module, we learned that **`LLMTestCase` is the most fundamental object in DeepEval**.

Before DeepEval can evaluate anything, it first needs to know:

* What was the user's input?
* What did the LLM respond?
* (Optionally) What was the expected answer?
* (Optionally) What context was provided?

All of this information is stored inside an **`LLMTestCase`**.

Think of it as a **container** that holds everything about one evaluation example.

---

#### What is an `LLMTestCase`?

An `LLMTestCase` represents **one interaction** between a user and an LLM.

For a simple chatbot:

```text
User
│
├── Question:
│   What is Python?
│
└── LLM
    │
    └── Response:
        Python is a programming language.
```

This entire interaction becomes one test case.

---

#### Importing `LLMTestCase`

Import it using:

```python
from deepeval.test_case import LLMTestCase
```

Notice it comes from the **`test_case`** module.

---

#### Creating Your First Test Case

The simplest possible test case is:

```python
test_case = LLMTestCase(
    input="What is Python?",
    actual_output="Python is a programming language."
)
```

This is all you need for many beginner metrics such as **Answer Relevancy**.

---

#### Understanding Every Parameter

Although the constructor supports many fields, you don't need all of them.

Let's understand them one by one.

---

#### 1. `input`

#### What is it?

The **input** is what your application receives.

For a chatbot, it is simply the user's question.

Example:

```python
input="What is Machine Learning?"
```

Think of it as:

```text
User
 │
 ▼
Question
```

---

#### 2. `actual_output`

#### What is it?

This is the response generated by your LLM.

Example:

```python
actual_output="Machine Learning is a branch of Artificial Intelligence..."
```

Think of it as:

```text
Question
     │
     ▼
Chatbot
     │
     ▼
actual_output
```

This field is called **actual output** because it is the **actual answer produced by your application**, not what you expected it to produce.

---

#### Required Fields

For a simple chatbot, only two fields are required.

```python
test_case = LLMTestCase(
    input="What is Python?",
    actual_output="Python is a programming language."
)
```

These are enough for metrics like:

* Answer Relevancy
* Toxicity
* Bias

---

#### Optional Fields

As your application becomes more sophisticated, you'll provide additional information.

---

#### 1. `expected_output`

Example:

```python
expected_output="Python is a high-level programming language."
```

#### Why is it useful?

Some evaluations compare:

* What the model actually said
* What you expected it to say

Example:

```text
Expected:
Python is a programming language.

Actual:
Python is a snake.
```

Clearly something went wrong.

Not every metric requires an expected output.

---

#### 2. `context`

Suppose you ask:

> Explain this paragraph.

The paragraph itself becomes the context.

Example:

```python
context=[
    "Python was created by Guido van Rossum."
]
```

The LLM should answer using this information.

---

#### 3. `retrieval_context`

This is mostly used for **RAG applications**.

Example:

```python
retrieval_context=[
    "Document 1...",
    "Document 2...",
    "Document 3..."
]
```

These are the documents retrieved from your vector database before the LLM generated its answer.

Metrics such as **Faithfulness** and **Context Precision** use this field.

---

#### 4. `tools_called`

Suppose your AI agent used tools.

Example:

```text
Weather API

Calculator

Search API
```

DeepEval can verify whether the correct tools were called.

Example:

```python
tools_called=[...]
```

We'll learn this later in the Agent Evaluation section.

---

#### 5. `expected_tools`

Sometimes you already know which tool should have been used.

Example:

```text
Expected:

Calculator

Actual:

Search API
```

DeepEval can compare them.

---

#### Complete Example

Here's a more complete test case.

```python
test_case = LLMTestCase(
    input="What is Python?",
    actual_output="Python is a programming language.",
    expected_output="Python is a high-level programming language.",
    context=[
        "Python was created by Guido van Rossum."
    ],
    retrieval_context=[
        "Python is an interpreted programming language."
    ]
)
```

Don't worry if some of these fields don't make sense yet. We'll explore each one in detail in later modules.

---

#### Which Fields Should I Use?

That depends on your application.

#### Simple Chatbot

```python
LLMTestCase(
    input=...,
    actual_output=...
)
```

---

#### Chatbot with Ground Truth

```python
LLMTestCase(
    input=...,
    actual_output=...,
    expected_output=...
)
```

---

#### RAG Application

```python
LLMTestCase(
    input=...,
    actual_output=...,
    retrieval_context=[...]
)
```

---

#### AI Agent

```python
LLMTestCase(
    input=...,
    actual_output=...,
    tools_called=[...],
    expected_tools=[...]
)
```

Notice that **the same `LLMTestCase` class is used for all application types**. You simply provide the fields that are relevant to your evaluation.

---

#### Required vs Optional Fields

| Field               | Required | Used For                                |
| ------------------- | -------- | --------------------------------------- |
| `input`             | ✅ Yes    | User input                              |
| `actual_output`     | ✅ Yes    | LLM response                            |
| `expected_output`   | ❌ No     | Compare with a known correct answer     |
| `context`           | ❌ No     | Additional information given to the LLM |
| `retrieval_context` | ❌ No     | Retrieved documents in RAG              |
| `tools_called`      | ❌ No     | Agent tool usage                        |
| `expected_tools`    | ❌ No     | Validate expected tool usage            |

---

#### Mental Model

Think of `LLMTestCase` as a folder containing everything about one interaction.

```text
LLMTestCase
│
├── input
├── actual_output
├── expected_output
├── context
├── retrieval_context
├── tools_called
└── expected_tools
```

Some evaluations only open two files in the folder (`input` and `actual_output`).

Other evaluations may use four or five files.

The important thing is that **all information related to a single evaluation is kept together in one object**.

---

#### Key Takeaways

* `LLMTestCase` represents **one evaluation example**.
* It is imported using:

```python
from deepeval.test_case import LLMTestCase
```

* The two required fields are:

  * `input`
  * `actual_output`
* Additional fields such as `expected_output`, `context`, `retrieval_context`, and `tools_called` are optional and are used only by specific metrics.
* The same `LLMTestCase` class works for simple chatbots, RAG systems, and AI agents—you simply populate the fields that are relevant to your application.

In the next module, we'll explore **metrics** in detail, starting with **AnswerRelevancyMetric**, and learn how a metric uses the information stored in an `LLMTestCase` to produce a score.

## Module 2: Metric

# Your First Metric

In the previous module, we learned how to create an `LLMTestCase`, which stores everything about an LLM interaction. However, **storing the data alone is not enough**. We still need a way to determine **what aspect of the response should be evaluated**.

This is where **Metrics** come in.

---

# What is a Metric?

A **Metric** defines **what you want to evaluate** in an LLM response.

Think of it as the **evaluation criteria**.

For example, imagine a teacher grading an exam.

The teacher may evaluate:

* Correctness
* Grammar
* Handwriting
* Presentation

Each of these is a different evaluation criterion.

Similarly, DeepEval can evaluate:

* Answer Relevancy
* Faithfulness
* Hallucination
* Toxicity
* Bias
* Context Precision

Each of these is a separate **metric**.

---

# Why Do We Need Metrics?

Consider the following chatbot.

**User**

> What is Python?

**LLM**

> Python is a programming language.

Now ask yourself:

What do you want to evaluate?

* Is the answer relevant?
* Is the answer factually correct?
* Is it hallucinating?
* Is it toxic?
* Is it biased?

There isn't a single "quality score."

Different applications care about different qualities.

That's why DeepEval provides multiple metrics.

---

# Importing a Metric

Metrics are imported from the `deepeval.metrics` module.

Example:

```python
from deepeval.metrics import AnswerRelevancyMetric
```

Every metric has its own class.

For example:

```python
from deepeval.metrics import FaithfulnessMetric
```

```python
from deepeval.metrics import HallucinationMetric
```

```python
from deepeval.metrics import ToxicityMetric
```

Each metric is responsible for evaluating a different aspect of the LLM's response.

---

# Creating Your First Metric

Creating a metric is very simple.

```python
metric = AnswerRelevancyMetric()
```

Notice something important.

This line **does not perform any evaluation**.

It simply creates a metric object.

Think of it like creating a calculator.

```python
calculator = Calculator()
```

The calculator doesn't perform any calculation until you ask it to.

Similarly,

```python
metric = AnswerRelevancyMetric()
```

doesn't calculate any score.

It only prepares the metric.

---

# What Happens Internally?

When you create

```python
metric = AnswerRelevancyMetric()
```

DeepEval creates an object that contains all the logic required to evaluate answer relevancy.

Conceptually,

```text
AnswerRelevancyMetric

│

├── Evaluation Prompt

├── Scoring Logic

├── Threshold

├── Judge LLM Configuration

└── measure() Method
```

No LLM is called yet.

No score is generated yet.

---

# When Is the Judge LLM Called?

Many beginners assume this:

```python
metric = AnswerRelevancyMetric()
```

↓

Judge LLM

↓

Score

This is **incorrect**.

The Judge LLM is only called later when you execute:

```python
evaluate(
    test_cases=[test_case],
    metrics=[metric]
)
```

At that point,

DeepEval internally calls something similar to:

```python
metric.measure(test_case)
```

The metric then:

* Reads the required fields from the `LLMTestCase`
* Builds an evaluation prompt
* Sends the prompt to the Judge LLM
* Receives a score and reasoning
* Returns the result

---

# Understanding the Constructor

The simplest constructor is:

```python
metric = AnswerRelevancyMetric()
```

This uses the default configuration.

However, metrics usually allow you to customize their behavior.

For example,

```python
metric = AnswerRelevancyMetric(
    threshold=0.7
)
```

Here,

```text
threshold = 0.7
```

means:

The evaluation passes only if the score is **0.7 or higher**.

Example:

| Score | Result |
| ----- | ------ |
| 0.95  | ✅ Pass |
| 0.82  | ✅ Pass |
| 0.69  | ❌ Fail |
| 0.40  | ❌ Fail |

---

# Another Constructor Example

You may also specify which Judge LLM to use.

Conceptually,

```python
metric = AnswerRelevancyMetric(
    model=my_judge_model
)
```

This tells DeepEval:

> Use this model when evaluating responses.

The Judge LLM can be:

* OpenAI
* Claude
* Gemini
* Ollama
* Azure OpenAI
* Or your own custom model

The generator model and the judge model are independent.

For example,

```text
Generator Model

↓

Claude

↓

Answer

↓

Judge Model

↓

GPT-4.1
```

or

```text
Generator Model

↓

GPT-4.1

↓

Answer

↓

Judge Model

↓

Claude
```

Both are valid.

---

# One Metric vs Multiple Metrics

You are not limited to a single metric.

Example:

```python
metrics = [
    AnswerRelevancyMetric(),
    FaithfulnessMetric(),
    HallucinationMetric()
]
```

Then,

```python
evaluate(
    test_cases=[test_case],
    metrics=metrics
)
```

Each metric evaluates the same response independently.

```text
                Same Response

                     │

        ┌────────────┼─────────────┐

        ▼            ▼             ▼

Relevancy     Faithfulness   Hallucination

      │             │             │

   Score 1       Score 2      Score 3
```

Each metric answers a different question.

---

# How Does a Metric Know What to Evaluate?

Remember the previous module.

`LLMTestCase` may contain:

```text
input

actual_output

expected_output

retrieval_context

tools_called

expected_tools
```

The metric decides which fields it needs.

For example,

**AnswerRelevancyMetric**

uses mainly:

```text
input

actual_output
```

**FaithfulnessMetric**

uses:

```text
actual_output

retrieval_context
```

**Tool Correctness Metric**

uses:

```text
tools_called

expected_tools
```

Metrics ignore the fields they don't need.

---

# Mental Model

Think of a metric as a specialist.

```text
LLMTestCase

        │

        ▼

Metric

        │

Reads only relevant fields

        │

Builds evaluation prompt

        │

Calls Judge LLM (if required)

        │

Returns

Score

Reason

Pass / Fail
```

---

# Complete Example

```python
from deepeval.metrics import AnswerRelevancyMetric

metric = AnswerRelevancyMetric(
    threshold=0.7
)
```

Later, we'll use it together with a test case.

```python
evaluate(
    test_cases=[test_case],
    metrics=[metric]
)
```

---

# Key Takeaways

* A **Metric** defines **what aspect** of an LLM response should be evaluated.
* Metrics are imported from the `deepeval.metrics` module.
* Creating a metric object (e.g., `AnswerRelevancyMetric()`) **does not perform any evaluation**.
* Most metrics allow you to configure options such as `threshold` and the **Judge LLM** through the constructor.
* The actual evaluation happens only when `evaluate()` calls the metric's internal `measure()` method.
* Different metrics use different fields from the same `LLMTestCase`.
* Multiple metrics can evaluate the same response independently, producing separate scores and reasoning for different quality dimensions.
* **Mental Model:** `LLMTestCase` provides the data, the **Metric** decides how to evaluate it, and `evaluate()` orchestrates the entire process.

## Module 3: evaluate()

# Running Your First Evaluation

So far, we've learned two important building blocks of DeepEval:

* **`LLMTestCase`** → Stores the data to be evaluated.
* **`Metric`** → Defines what aspect of the response should be evaluated.

Now it's time to connect them together and perform our **first evaluation** using the `evaluate()` function.

---

# What is `evaluate()`?

The `evaluate()` function is the **entry point** for running evaluations in DeepEval.

Its job is to:

1. Receive one or more test cases.
2. Receive one or more metrics.
3. Execute each metric on each test case.
4. Collect the results.
5. Display a report.

Think of it as the **orchestrator** of the evaluation process.

It **does not** calculate the score itself. Instead, it coordinates the evaluation by asking each metric to evaluate the test case.

---

# Importing `evaluate`

Import it using:

```python
from deepeval import evaluate
```

This is the main function you'll use in almost every DeepEval project.

---

# Passing Test Cases

The first argument is a list of test cases.

Example:

```python
test_case = LLMTestCase(
    input="What is Python?",
    actual_output="Python is a programming language."
)
```

Pass it to `evaluate()`:

```python
evaluate(
    test_cases=[test_case]
)
```

Notice that even though we have only **one** test case, we still pass it as a **list**.

Why?

Because DeepEval is designed to evaluate **multiple test cases**.

For example:

```python
test_cases = [
    test_case1,
    test_case2,
    test_case3
]
```

This makes it easy to evaluate hundreds or even thousands of examples in a single run.

---

# Passing Metrics

The second argument is a list of metrics.

Example:

```python
metric = AnswerRelevancyMetric()
```

Pass it like this:

```python
evaluate(
    test_cases=[test_case],
    metrics=[metric]
)
```

Again, notice that metrics are also passed as a list.

This allows you to evaluate the same response using multiple metrics.

Example:

```python
metrics = [
    AnswerRelevancyMetric(),
    FaithfulnessMetric(),
    HallucinationMetric()
]
```

Then:

```python
evaluate(
    test_cases=[test_case],
    metrics=metrics
)
```

Each metric evaluates the response independently.

---

# Complete Example

```python
from deepeval import evaluate
from deepeval.test_case import LLMTestCase
from deepeval.metrics import AnswerRelevancyMetric

test_case = LLMTestCase(
    input="What is the capital of France?",
    actual_output="The capital of France is Paris."
)

metric = AnswerRelevancyMetric(
    threshold=0.7
)

evaluate(
    test_cases=[test_case],
    metrics=[metric]
)
```

This is the smallest complete DeepEval program.

---

# What Happens Behind the Scenes?

When you run:

```python
evaluate(
    test_cases=[test_case],
    metrics=[metric]
)
```

DeepEval performs something conceptually similar to:

```python
for test_case in test_cases:

    for metric in metrics:

        result = metric.measure(test_case)

        save(result)

print_report()
```

Notice that:

* `evaluate()` loops through every test case.
* For each test case, it loops through every metric.
* Each metric evaluates the test case independently.
* Finally, DeepEval displays the evaluation results.

---

# Evaluation Flow

```text
             evaluate()

                  │

      Receives Test Cases

                  │

      Receives Metrics

                  │

     Loop over every test case

                  │

       Loop over every metric

                  │

      metric.measure(test_case)

                  │

       Judge LLM (if required)

                  │

          Score + Reason

                  │

        Collect all results

                  │

        Display final report
```

---

# Reading the Output

A typical output looks similar to:

```text
====================================================
Answer Relevancy
====================================================

Score: 1.0

Threshold: 0.7

Success: True

Reason:
The answer directly addresses the user's question
and is completely relevant.
```

Let's understand each part.

---

## Score

Example:

```text
Score: 0.92
```

This is the score assigned by the metric.

Most LLM-based metrics return a score between:

```text
0.0 → Poor

1.0 → Excellent
```

Higher scores indicate better performance.

---

## Threshold

Example:

```text
Threshold: 0.7
```

This is the minimum score required to pass.

If:

```text
Score >= Threshold
```

the evaluation passes.

Otherwise, it fails.

---

## Success

Example:

```text
Success: True
```

This is simply the pass/fail result.

Example:

| Score | Threshold | Success |
| ----- | --------- | ------- |
| 0.95  | 0.70      | ✅ True  |
| 0.81  | 0.70      | ✅ True  |
| 0.60  | 0.70      | ❌ False |

---

## Reason

Example:

```text
Reason:

The answer is directly relevant to the user's
question and contains no unrelated information.
```

One of the most useful outputs is the **reason**.

Instead of only providing a number, DeepEval explains **why** the score was assigned.

This helps developers understand how to improve their application.

---

# Multiple Metrics Output

Suppose you evaluate using:

```python
metrics = [
    AnswerRelevancyMetric(),
    HallucinationMetric(),
    FaithfulnessMetric()
]
```

DeepEval produces a separate result for each metric.

Conceptually:

```text
Answer Relevancy

Score: 1.0

------------------------

Faithfulness

Score: 0.95

------------------------

Hallucination

Score: 0.98
```

Each metric measures a different quality of the same response.

---

# Multiple Test Cases

Suppose you evaluate:

```python
test_cases = [
    tc1,
    tc2,
    tc3
]
```

DeepEval repeats the process for each test case.

Conceptually:

```text
Test Case 1

    Relevancy

    Hallucination

------------------------

Test Case 2

    Relevancy

    Hallucination

------------------------

Test Case 3

    Relevancy

    Hallucination
```

This makes it easy to evaluate large datasets.

---

# Mental Model

Whenever you see:

```python
evaluate(
    test_cases=[...],
    metrics=[...]
)
```

Think of it like this:

```text
evaluate()

│

├── Read all test cases

├── Read all metrics

├── For every test case

│      └── Run every metric

├── Collect scores

├── Collect reasons

└── Display the evaluation report
```

Remember:

* **`LLMTestCase`** stores the evaluation data.
* **Metrics** decide what to evaluate.
* **`evaluate()`** coordinates the entire evaluation process.

---

# Key Takeaways

* Import `evaluate()` using:

  ```python
  from deepeval import evaluate
  ```
* `evaluate()` is the main function used to execute evaluations in DeepEval.
* Pass one or more `LLMTestCase` objects using the `test_cases` parameter.
* Pass one or more metrics using the `metrics` parameter.
* Both `test_cases` and `metrics` are lists, allowing DeepEval to evaluate multiple examples and multiple quality dimensions in one run.
* `evaluate()` does not compute scores itself; it delegates the work to each metric.
* Most metrics return a **Score**, **Threshold**, **Success (Pass/Fail)**, and a **Reason** explaining the evaluation.
* **Mental Model:** `evaluate()` is an orchestrator that loops through all test cases and metrics, executes the evaluations, collects the results, and presents a readable report.

## Module 4: Understand the Result 

# Module 8: Understanding the Evaluation Result

In the previous module, we learned how to execute an evaluation using the `evaluate()` function.

After the evaluation completes, DeepEval displays a report containing information such as:

```text
Score: 0.91

Success: True

Reason:
The answer is relevant to the question.
```

At first glance, this output looks simple, but understanding what each field means is very important. In this module, we'll learn how to interpret these evaluation results.

---

# A Typical Evaluation Result

Suppose we evaluated our chatbot using `AnswerRelevancyMetric`.

```python
metric = AnswerRelevancyMetric(
    threshold=0.7
)

evaluate(
    test_cases=[test_case],
    metrics=[metric]
)
```

DeepEval may produce an output similar to:

```text
=================================================
Answer Relevancy
=================================================

Score: 0.91

Threshold: 0.70

Success: True

Reason:
The answer directly addresses the user's question
without including irrelevant information.
```

Let's understand each field one by one.

---

# 1. What is a Score?

The **score** represents **how well the LLM performed according to the selected metric**.

Example:

```text
Score: 0.91
```

Most DeepEval metrics return a score between:

```text
0.0  --------------------------->  1.0

Poor                           Excellent
```

Generally,

* **1.0** → Excellent
* **0.8 - 0.9** → Very Good
* **0.6 - 0.8** → Acceptable
* **Below 0.6** → Needs Improvement

> **Note:** The meaning of the score depends on the metric. A score of **0.9 in Answer Relevancy** is not the same as **0.9 in Hallucination** because each metric measures a different quality.

---

# How is the Score Generated?

For most semantic metrics, the score is generated by a **Judge LLM**.

Conceptually:

```text
User Question
      │
      ▼
LLM Response
      │
      ▼
Metric
      │
      ▼
Judge LLM
      │
      ▼
Score (0 - 1)
```

The Judge LLM reads the evaluation prompt created by the metric and assigns an appropriate score.

---

# 2. What is Success?

Example:

```text
Success: True
```

`Success` is simply a **Boolean value** (`True` or `False`) indicating whether the evaluation passed.

It is calculated by comparing the **Score** with the **Threshold**.

---

# How is Success Determined?

Imagine your metric was configured as:

```python
metric = AnswerRelevancyMetric(
    threshold=0.7
)
```

Now suppose the Judge LLM returns:

```text
Score: 0.91
```

Since:

```text
0.91 >= 0.70
```

DeepEval returns:

```text
Success: True
```

If instead the score was:

```text
Score: 0.55
```

then:

```text
0.55 < 0.70
```

Result:

```text
Success: False
```

---

# Score vs Success

Think of it this way:

* **Score** tells you **how good** the response is.
* **Success** tells you **whether it met your quality requirement**.

Example:

| Score | Threshold | Success |
| ----- | --------- | ------- |
| 0.95  | 0.70      | ✅ True  |
| 0.82  | 0.70      | ✅ True  |
| 0.71  | 0.70      | ✅ True  |
| 0.69  | 0.70      | ❌ False |
| 0.45  | 0.70      | ❌ False |

---

# 3. What is a Reason?

The **Reason** explains **why the Judge LLM assigned the score**.

Example:

```text
Reason:
The answer directly addresses the user's question
and contains no irrelevant information.
```

Instead of only returning a number, DeepEval provides a human-readable explanation.

This is one of the most valuable features of DeepEval because it helps developers understand **why an evaluation passed or failed**.

---

# Another Example

Suppose the chatbot answers:

> Python was invented by Elon Musk.

The output might be:

```text
Score: 0.18

Success: False

Reason:
The response contains incorrect factual information
that is unrelated to the user's question.
```

Without the reason, you would only know that the score is low.

With the reason, you immediately understand what needs to be fixed.

---

# 4. What is a Threshold?

The **threshold** is the **minimum score required to pass the evaluation**.

Example:

```python
metric = AnswerRelevancyMetric(
    threshold=0.7
)
```

Here,

```text
Threshold = 0.70
```

This means:

```text
If Score >= 0.70

↓

Pass

Otherwise

↓

Fail
```

---

# Why Do We Need a Threshold?

Suppose your chatbot is used in customer support.

You may require:

```text
Threshold = 0.90
```

because only highly relevant answers are acceptable.

For an internal prototype, you might use:

```text
Threshold = 0.60
```

since you're still experimenting.

The threshold depends on **how strict you want the evaluation to be**.

---

# How All Four Fields Work Together

Imagine this evaluation result:

```text
Score: 0.84

Threshold: 0.80

Success: True

Reason:
The answer is relevant but could include
slightly more detail.
```

Interpretation:

* The Judge LLM gave a score of **0.84**.
* The minimum required score was **0.80**.
* Since **0.84 ≥ 0.80**, the evaluation passed.
* The reason explains why the score wasn't perfect.

---

# Complete Evaluation Flow

```text
LLMTestCase
      │
      ▼
Metric
      │
      ▼
Judge LLM
      │
      ▼
Score
      │
      ▼
Compare with Threshold
      │
      ▼
Success (True / False)
      │
      ▼
Generate Reason
      │
      ▼
Display Report
```

Notice that all four fields are connected.

The **Score** is produced first.

The **Threshold** is predefined by you.

DeepEval compares them to determine **Success**.

Finally, the Judge LLM provides a **Reason** explaining the evaluation.

---

# How Should Developers Use These Results?

When evaluating an AI application:

* Look at the **Score** to understand the quality level.
* Check **Success** to see whether the response met your quality requirement.
* Read the **Reason** to understand why the score was assigned.
* Adjust the **Threshold** based on your application's requirements and desired level of quality.

Looking only at **Success** is usually not enough. The **Reason** often provides the most actionable insights for improving your prompts, retrieval pipeline, or model behavior.

---

# Mental Model

Whenever you see:

```text
Score: 0.91

Threshold: 0.70

Success: True

Reason:
The answer is relevant.
```

Think of it like this:

```text
Judge LLM
      │
      ▼
Assign Score
      │
      ▼
Compare with Threshold
      │
      ▼
Pass or Fail
      │
      ▼
Explain the Decision
```

---

# Key Takeaways

* **Score** measures how well the LLM performed for the selected metric, typically on a scale from **0.0 to 1.0**.
* **Success** is a Boolean (`True` or `False`) that indicates whether the score met the required threshold.
* **Reason** is a human-readable explanation generated by the Judge LLM that explains why the score was assigned.
* **Threshold** is the minimum acceptable score that determines whether the evaluation passes or fails.
* For most semantic metrics, the **Judge LLM** generates the score and reason, while DeepEval compares the score against the threshold to determine the success status.
* The best way to interpret an evaluation is to consider **all four fields together**, not just the final pass/fail result.

## Module 5: Understand different metrics 

# Module 10: Understanding DeepEval Metrics

Up to this point, we've learned:

* How to create an `LLMTestCase`
* How to create a `Metric`
* How `evaluate()` works
* How to interpret the evaluation results

Now comes the most important part of DeepEval:

> **Understanding what each metric actually measures.**

A common misconception among beginners is:

> "All metrics are just asking another LLM whether the answer is good."

This is **not true**.

Each metric asks a **different evaluation question** and therefore measures a different aspect of the response.

---

# How Should You Think About Metrics?

Imagine you have the following answer:

**Question**

> Explain Machine Learning.

**LLM Answer**

> Machine Learning is a subset of Artificial Intelligence that enables computers to learn patterns from data without being explicitly programmed. It is widely used in recommendation systems, fraud detection, image recognition, and many other applications.

Is this answer good?

Well...

That depends.

You could ask:

* Is it relevant?
* Is it factually correct?
* Did it use only the provided context?
* Is it biased?
* Is it toxic?

Each question requires a different metric.

---

# How Does a Metric Evaluate a Long Paragraph?

This is one of the most important concepts to understand.

Suppose your chatbot generates this answer:

```text
Machine Learning is a subset of Artificial Intelligence that enables
computers to learn from data.

It is widely used in recommendation systems,
autonomous driving,
medical diagnosis,
fraud detection,
weather prediction,
and robotics.

There are three major categories:

• Supervised Learning
• Unsupervised Learning
• Reinforcement Learning
```

This isn't a single sentence.

It contains:

* Multiple facts
* Multiple claims
* Multiple examples

How does DeepEval evaluate it?

---

## It Does NOT Score Sentence by Sentence

Many beginners imagine something like:

```text
Sentence 1 → Score

Sentence 2 → Score

Sentence 3 → Score

Average Score
```

DeepEval generally **does not** work like this.

---

## The Judge LLM Reads the Entire Response

Instead, the metric constructs an evaluation prompt containing:

* User question
* LLM answer
* (Optional) retrieved context
* Evaluation instructions

Conceptually:

```text
You are an expert evaluator.

Question:
Explain Machine Learning.

Answer:
...

Evaluate whether this answer is relevant.

Return:

Score
Reason
```

The Judge LLM evaluates the **overall response**, just as a human reviewer would.

It considers:

* Whether the answer addresses the question.
* Whether important information is missing.
* Whether irrelevant information is included.
* Whether the overall response satisfies the evaluation criteria.

It is **not** simply averaging sentence-level scores.

---

# Why Can Different Answers Both Receive High Scores?

Consider this question:

> Explain Python.

### Answer A

```text
Python is a programming language.
```

### Answer B

```text
Python is a high-level interpreted programming language
created by Guido van Rossum.
It is widely used for AI,
web development,
automation,
and data science.
```

Both answers are correct.

Answer B is more detailed.

DeepEval does **not** expect one exact wording.

Instead, the Judge LLM evaluates whether the answer satisfies the metric being measured.

This is why LLM-based evaluation is much more flexible than exact string matching.

---

# 1. Answer Relevancy Metric

## Why does it exist?

To answer one simple question:

> **Did the LLM actually answer the user's question?**

Many LLMs produce responses that are:

* Too broad
* Off-topic
* Partially relevant

This metric detects that.

---

## Required Inputs

```text
input

actual_output
```

---

## What Does It Measure?

It measures whether the generated answer is relevant to the user's query.

Example:

**Question**

> What is Python?

**Answer**

> Python is a programming language.

Score:

```text
High
```

---

Bad example:

**Question**

> What is Python?

**Answer**

> The Eiffel Tower is in Paris.

Score:

```text
Very Low
```

---

## Common Mistakes

* Assuming it checks factual correctness.
* Assuming it checks hallucinations.

It doesn't.

It only asks:

> **"Did the answer address the question?"**

---

# 2. Faithfulness Metric

## Why does it exist?

RAG applications retrieve documents.

The LLM should answer **using only those retrieved documents**.

Faithfulness checks whether it did.

---

## Required Inputs

```text
actual_output

retrieval_context
```

---

## What Does It Measure?

It checks whether every important claim in the answer is supported by the retrieved context.

---

Example

Retrieved Context

```text
Python was created by Guido van Rossum.
```

LLM Answer

```text
Python was created by Guido van Rossum.
```

Score:

```text
High
```

---

Bad Answer

```text
Python was created by Elon Musk.
```

Score:

```text
Low
```

because the retrieved context never mentioned Elon Musk.

---

## Common Mistakes

People think Faithfulness means:

> "Is the answer correct?"

Not exactly.

It means:

> **"Is the answer supported by the retrieved context?"**

The retrieved context itself could even be wrong.

---

# 3. Hallucination Metric

## Why does it exist?

LLMs sometimes invent facts.

This is called hallucination.

---

## Required Inputs

```text
actual_output

retrieval_context
```

---

## What Does It Measure?

It checks whether the model introduced unsupported or fabricated information.

Example

Retrieved Context

```text
Python was created by Guido van Rossum.
```

Answer

```text
Python was created by Guido van Rossum
and first released by Microsoft.
```

The Microsoft claim isn't supported.

Hallucination score becomes worse.

---

## Common Mistakes

People often confuse Hallucination and Faithfulness.

In practice they are closely related, but they answer slightly different questions:

Faithfulness:

> "Did you stay faithful to the provided evidence?"

Hallucination:

> "Did you invent unsupported facts?"

---

# 4. Bias Metric

## Why does it exist?

AI systems should produce fair and balanced responses.

Bias Metric detects unfair or prejudiced language.

---

## Required Inputs

```text
actual_output
```

---

## What Does It Measure?

It evaluates whether the response contains unfair assumptions or stereotypes.

Example

```text
Women cannot become engineers.
```

High bias.

---

Balanced answer

```text
Engineering is a profession open to everyone
regardless of gender.
```

Low bias.

---

## Common Mistakes

Bias is not the same as toxicity.

A response can be polite but still biased.

---

# 5. Toxicity Metric

## Why does it exist?

Applications shouldn't produce abusive or offensive responses.

---

## Required Inputs

```text
actual_output
```

---

## What Does It Measure?

It checks for:

* Hate speech
* Insults
* Harassment
* Threats
* Offensive language

---

Example

```text
You are an idiot.
```

High toxicity.

---

Example

```text
I disagree with your opinion.
```

Not toxic.

---

## Common Mistakes

Being critical is not necessarily toxic.

The metric distinguishes disagreement from abusive language.

---

# Other Important Metrics

Besides the five metrics above, there are several others that are commonly used in real-world applications.

---

## Contextual Relevancy

### Why?

In RAG, not every retrieved document is useful.

### Measures

Whether the retrieved context is actually relevant to the user's question.

Inputs:

```text
input

retrieval_context
```

---

## Context Precision

### Why?

Retrievers often return too many irrelevant chunks.

### Measures

How much of the retrieved context is actually useful.

Higher precision means fewer irrelevant documents.

---

## Context Recall

### Why?

The retriever might miss important documents.

### Measures

Whether the retrieved context contains the information needed to answer the question.

---

## Tool Correctness (Agent Evaluation)

### Why?

AI agents frequently call external tools.

### Measures

Whether the correct tools were selected and executed.

Inputs:

```text
tools_called

expected_tools
```

---

## Summarization

### Why?

Many applications summarize long documents.

### Measures

Whether the summary captures the important information while remaining concise and accurate.

---

# Which Metrics Should You Use?

It depends on your application.

| Application            | Recommended Metrics                                                              |
| ---------------------- | -------------------------------------------------------------------------------- |
| Chatbot                | Answer Relevancy, Bias, Toxicity                                                 |
| RAG                    | Answer Relevancy, Faithfulness, Hallucination, Context Precision, Context Recall |
| AI Agent               | Answer Relevancy, Tool Correctness, Bias, Toxicity                               |
| Document Summarization | Summarization, Faithfulness, Answer Relevancy                                    |

---

# Mental Model

Every metric asks a different question.

```text
LLM Response
      │
      ├────────────► Answer Relevancy
      │              "Did it answer the question?"
      │
      ├────────────► Faithfulness
      │              "Did it use the retrieved evidence?"
      │
      ├────────────► Hallucination
      │              "Did it invent unsupported facts?"
      │
      ├────────────► Bias
      │              "Is it fair and unbiased?"
      │
      ├────────────► Toxicity
      │              "Is it safe and respectful?"
      │
      ├────────────► Context Precision
      │              "Were the retrieved documents useful?"
      │
      ├────────────► Context Recall
      │              "Was important context retrieved?"
      │
      └────────────► Tool Correctness
                     "Did the agent use the correct tools?"
```

---

# Key Takeaways

* A metric measures **one specific quality** of an LLM response; there is no universal "goodness" metric.
* Most semantic metrics evaluate the **entire response**, not individual sentences, just like a human reviewer.
* Different correct answers can receive high scores because LLM-based evaluation focuses on meaning rather than exact wording.
* **Answer Relevancy** checks whether the response answers the user's question.
* **Faithfulness** verifies that the response is supported by the retrieved context.
* **Hallucination** detects information that is not supported by the available evidence.
* **Bias** evaluates fairness and looks for stereotypes or prejudiced language.
* **Toxicity** detects harmful, abusive, or offensive content.
* For RAG systems, **Context Precision** and **Context Recall** are just as important as Faithfulness because they evaluate retrieval quality.
* For AI agents, **Tool Correctness** ensures that the agent selected and used the appropriate tools.
* The best metrics depend on your application. Chatbots, RAG systems, AI agents, and summarization systems each require different evaluation criteria.
